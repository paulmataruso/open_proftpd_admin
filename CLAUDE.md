# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A self-hosted, Dockerized web portal for managing ProFTPd virtual users and an HTTP downloads site (nginx `.htpasswd`), with real-time download/upload activity tracking. Users self-register or are admin-provisioned; admins get a dashboard for user management, audit logs, download/upload stats, and abuse controls (IP/username bans, intrusion detection).

**Crucial fact:** ProFTPd and the public-facing downloads nginx are **not** part of this docker-compose stack — they run as system services directly on the host (`systemctl {reload,status} proftpd`). This stack only *generates the config files those services read* (`ftpd.passwd`, `ftpd_trusted.conf`, `.htpasswd`) and *ingests their logs*. Don't look for ProFTPd inside a container. The one piece of this project that runs **on the host, outside compose**, is the ftpwho exporter (`ciosuseradd-ftpwho.service`, see *Live FTP sessions* below).

## Commands

```bash
docker compose up -d              # start/update the stack
docker compose build <service>    # rebuild an image after editing its source
docker compose up -d <service>    # recreate a container after editing .env or docker-compose.yml
docker compose logs -f <service>  # tail logs (backend, logtailer, nginx, db, db_logs, frontend)
docker compose ps
```

**`docker compose up -d <service>` alone does NOT pick up source code changes.** `backend/Dockerfile` and `logtailer/Dockerfile` `COPY . .` at build time, so editing anything under `backend/` or `logtailer/` requires `docker compose build <service>` before `up -d` (or `up -d --build`). A plain `.env`/`docker-compose.yml`-only change just needs `up -d <service>` — no rebuild, since env vars are injected at container-create time.

There is no test suite or linter configured in this repo.

**Forcing a config regeneration without a DB write:** `POST /admin/sync` (admin JWT required) re-runs `regenerate_ftpd_passwd()` + `regenerate_ftpd_trusted_conf()` + `regenerate_htpasswd()` against current DB state and current `settings` — use it after changing `FTP_UID`/`FTP_GID`/`TRUSTED_FTP_GID` in `.env` and restarting `backend`, to rewrite existing users' passwd-file entries without touching each one via the UI. The `/docs` endpoint is disabled and the backend isn't exposed on a host port directly (only via the `nginx` container's `/api/` proxy), so calling admin endpoints ad hoc from the host means `docker exec ciosuseradd_backend python3 -c '...'` (or `curl`) against `http://127.0.0.1:8000` from inside the container — plain `wget` busybox inside the alpine image doesn't support JSON POST bodies cleanly, `python3 -c` with `urllib.request` does.

## Architecture

### Containers and what they own

| Container | Owns |
|---|---|
| `nginx` | Reverse proxy, rate limiting, security headers, routes `/api/*` → backend, `/` → frontend |
| `frontend` | Static nginx serving `index.html` (auth'd admin/registration SPA) and `public.html` (unauth'd read-only dashboard) — `frontend/Dockerfile` COPYs each file individually, so a new frontend file needs an explicit `COPY` line added or it 404s silently |
| `backend` | FastAPI: all business logic, `ftpd.passwd`/`ftpd_trusted.conf`/`.htpasswd` generation, stats queries |
| `db` | Postgres — `users`, `trusted_ftp_users`, `admin_config`, `audit_log`, ban/intrusion tables |
| `db_logs` | Postgres — download/upload activity, isolated from `db` (separate network) |
| `logtailer` | Tails ProFTPd + nginx-downloads log files (host dirs, mounted read-only) into `db_logs` |

Three Docker networks: `internal` (nginx/frontend/backend), `db` (backend/db, internal-only), `db_logs` (backend/logtailer/db_logs, internal-only). `logtailer` has no route to `db` or to `internal`.

### Three FTP user classes — always handle them separately

- **Regular `User`** (table `users`): self-registered or admin-created, read-only FTP (chrooted to the global FTP root via `DefaultRoot` in `proftpd/virtualusers.conf`), also gets HTTP basic-auth access via `.htpasswd`.
- **`TrustedFtpUser`** (table `trusted_ftp_users`): admin-provisioned, full read/write, chrooted to their own directory under `FTP_BASE_PATH/<ftp_home_dir>` via a generated `<IfUser>` block. **Caveat:** that `DefaultRoot` is effectively ignored — `mod_ifsession` merges `<IfUser>` only *after* `mod_auth` has chrooted, so trusted users are really chrooted to the global FTP root and merely *start* in their home (which works only because it sits inside the global root).
- **`PrivateFtpUser`** (table `private_ftp_users`): admin-provisioned, full read/write, chrooted to `PRIVATE_FTP_BASE_PATH/<ftp_home_dir>` — a tree **separate** from `FTP_BASE_PATH`, never under the public root. Because of the `<IfUser>` caveat above, the chroot is `DefaultRoot ~ <PRIVATE_FTP_GROUP>` (evaluated at login), so every private user gets `PRIVATE_FTP_GID`, a dedicated host group nothing else may use. `ftpd_private.conf` also deny-alls the private base and locks each home with `AllowUser`; `Umask 027`. The backend creates the home folder itself (`/privateftp` mount, mode 750, `FTP_UID:PRIVATE_FTP_GID`); deleting the user keeps the folder. Private activity is filtered out of the public dashboard routes (`_is_private_path`, `_private_usernames`).

`backend/ftpfile.py`'s `regenerate_ftpd_passwd()` writes all three into one `ftpd.passwd` (ProFTPd allows only one `AuthUserFile`), in **separate loops** with separate GID sourcing (see below) — when touching UID/GID or permission logic, don't assume a single setting governs every class. `mod_auth_file` uses the first matching line, so usernames must be unique across all three tables — every create path goes through `ftp_username_taken()`.

`sync(db)` in `backend/main.py` is the central choke point: called after every `User`/`TrustedFtpUser`/`PrivateFtpUser` create/update/delete, it regenerates `ftpd.passwd` + `ftpd_trusted.conf` + `ftpd_private.conf` + `.htpasswd` atomically (temp file + rename). If you add a new mutation path for any of these tables, call `sync(db)` at the end of it.

### ProFTPd integration has two different refresh semantics

1. **`ftpd.passwd`** (`AuthUserFile`, read via `mod_auth_file`) — read fresh **per login**. A `/admin/sync` (or any action that triggers `sync()`) is immediately live for the next connection; no ProFTPd restart needed.
2. **`ftpd_trusted.conf`** / **`ftpd_private.conf`** (`<IfUser>` / `<Directory>` blocks, both `Include`d from the static `/etc/proftpd/proftpd.conf`) — parsed only at **ProFTPd startup/reload**. A brand-new trusted or private user (or any change to which `<IfUser>` blocks exist) needs `systemctl reload proftpd` on the host before it takes effect, even though `ftpd.passwd` itself is already updated. This is automated by the host-side `proftpd-reload/ciosuseradd-proftpd-reload.{path,service}` units (installed to `/etc/systemd/system/`, outside compose like ftpwho): the `.path` unit watches both generated conf files, and the oneshot service runs `proftpd --configtest` then `systemctl reload proftpd`. `_atomic_write()` in `ftpfile.py` skips identical rewrites so that the many `sync()` calls that don't change these files (e.g. regular-user registrations) don't trigger reloads — keep that skip if you touch it. `systemctl reload` is a graceful SIGHUP — it does not drop active transfers, and is the documented, expected way to apply this (see `proftpd/virtualusers.conf` header comments).

A freshly-created trusted-user home directory is owned `root:root` by default — the user's first `STOR`/`MKD` will get `550 Permission denied` until an admin runs `fix-permissions` (or manually chowns it) once.

### Ownership model for uploads (`FTP_UID`/`FTP_GID`/`TRUSTED_FTP_GID`)

- `settings.ftp_uid` / `settings.ftp_gid` (env `FTP_UID`/`FTP_GID`) apply **only** to regular + anonymous FTP users. They're read-only and can't create new content, so this GID choice doesn't affect upload ownership.
- `settings.trusted_ftp_gid` (env `TRUSTED_FTP_GID`, default `33`/www-data) is a **separate** setting used only for trusted users' `ftpd.passwd` lines, so their uploads land group-owned by the web server and stay readable by it — without touching regular/anon users' GID. Both classes share the same UID.
- `POST /admin/trusted/{id}/fix-permissions` recursively `chown`s an existing trusted user's *entire* home tree to `ftp_uid:trusted_ftp_gid` (not just the top-level directory) and `chmod`s directories `755`. Use it once right after creating a trusted user's home folder on the FTP host (see the permission-denied note above), and again if `TRUSTED_FTP_GID` is ever changed, to retroactively fix pre-existing uploads — new uploads after a `TRUSTED_FTP_GID` change + resync are correct automatically, no fix-permissions needed going forward.

### Live FTP sessions (ftpwho)

The admin "Live Sessions" panel (`panel-ftp-live` in `index.html`) shows `ftpwho -v` data in near-real-time. ProFTPd's scoreboard (`/run/proftpd.scoreboard`) can only be read reliably by the host's own `ftpwho` binary, so the data path is:

1. **Host:** `ftpwho/ftpwho-export.py` (installed as `/usr/local/sbin/ciosuseradd-ftpwho-export`, run by `ftpwho/ciosuseradd-ftpwho.service` → `/etc/systemd/system/`) runs `ftpwho -v -o json` every second and atomically writes `FTPWHO_DIR/ftpwho.json` (default `/var/lib/ciosuseradd/ftpwho`), wrapped with `generated_ms`/`ok`/`error`. Editing the script in the repo does nothing until it's re-copied to `/usr/local/sbin/` and `systemctl restart ciosuseradd-ftpwho`.
2. **Backend:** `FTPWHO_DIR` is bind-mounted read-only at `/ftpwho`; `GET /admin/ftpwho` (admin JWT) reads the file, normalizes each connection (`state` = download/upload/idle/command/auth, `user_class` = anon/registered/trusted/other via a lookup against `users`/`trusted_ftp_users`) and flags `stale` if the snapshot is >10s old. A missing file returns `ok:false` with an "is the exporter running?" error rather than a 5xx.
3. **Frontend:** polls every 1s only while the panel is open (`startLive`/`stopLive`, wired into `navTo`), pauses when the tab is hidden. Rendered as a stream: one long-lived row per pid (`_liveRows`, updated in place via `_liveSet` — never rebuild the list with innerHTML), stable order (newest connection first; never sort by rate/state or rows jump), a 100ms `liveFrame()` loop that extrapolates bytes at the measured rate between polls and eases toward each reading (rates smoothed), fade-in/out for arriving/leaving sessions and FLIP glide for reflow. No "snapshot age" text — the pill only changes on Stale/Offline/Error.

Gotchas:
- ftpwho 1.3.8's JSON field `transfer_duration_ms` is actually **microseconds** — the backend divides by 1000 to get `transfer_ms`. `connected_since_ms`/`idle_since_ms`/`started_ms` are real milliseconds.
- **Don't trust the scoreboard for transfer progress.** With `UseSendFile on`, ProFTPd barely updates per-transfer bytes, so ftpwho shows 0% / no rate for hours on big downloads. The exporter therefore enriches every connection with an `io` object from `/proc` (`IoTracker` in `ftpwho-export.py`): session `bytes_out`/`bytes_in` (wchar/rchar — sendfile counts toward both), `rate_out`/`rate_in` over a 10s window, `last_io_ms` (stall detection), `cmd_since_ms`, and `file` (path/size/offset/pct from `/proc/<pid>/fd` + `fdinfo`). Under sendfile the fd position stays at the REST offset, so offset = start position + rchar since the transfer began; when the position moves (FTPS uses read()+SSL_write) it's used directly. Transfers/commands already running when the exporter started are flagged `approx`/`cmd_since_approx`. `_ftpwho_conn()` prefers these over the scoreboard's `transfer_bytes`/`transfer_completed`, and the panel shows ≈ for estimates, ETA, a red "no data Xm" when a transfer has moved nothing for 30s, and the current command's duration under the connection age. The exporter needs root (it reads other processes' `/proc/<pid>/fd`).
- nginx gives `/api/admin/ftpwho` its own `ftpwho` limit_req zone (120 r/m). Don't route it through the shared `/api/` zone (30 r/m), or the 2s poller would starve the rest of the admin UI.

### FTP bans (anonymous idle / reconnect abuse)

Admin panel `panel-ftpban` ("FTP Bans"). Like ftpwho, the moving parts live **on the host, outside compose**:

1. **ProFTPd** writes a dedicated session log via `proftpd/ftpd_ban.conf` (→ `/etc/proftpd/ftpd_ban.conf`, `Include`d from `proftpd.conf`): `epoch|pid|ip|user|cmd|status|%E` for AUTH/READ commands and session `EXIT`. It lives in `/var/log/proftpd-ciosban/`, deliberately **not** in `FTP_LOG_DIR` (the logtailer ingests every archive in that dir). Rotated by `ftpban/ciosuseradd-ftpban.logrotate` (copytruncate).
2. **`ftpban/ftpban.py`** (→ `/usr/local/sbin/ciosuseradd-ftpban`, unit `ftpban/ciosuseradd-ftpban.service`, runs as root) tails that log, counts events **for anonymous sessions only** (`settings.anon_users`): `connect` (PASS 230), `notransfer`/`idle` (EXIT reason `TimeoutNoTransfer`/`TimeoutIdle`), `aborted` (RETR/STOR/APPE 426). Sliding windows per (event, IP) → auto bans. Owns the SQLite schema + default settings in `FTPBAN_DIR/ftpban.db` (tables `settings`, `bans`, `offenses` hourly counters, `status`).
3. **Enforcement is nftables**, table `inet ciosuseradd_ftpban` (sets `banned4`/`banned6` with per-element counters), reconciled every 2s against active bans; re-created automatically after a reboot. New connections from a banned IP to `settings.control_port` are `redirect`ed (nat prerouting + a local-only output chain) to a responder thread in the daemon on `settings.responder_port`, which sends `421 <message>` and closes — the message is per ban type (`settings.messages`: notransfer/idle/connect/aborted/manual, placeholders `{remaining}` `{expires}` `{ip}` `{reason}`). Direct (non-DNAT) connections to the responder port are reset. Everything else from a banned IP on `settings.ports` (passive data, sessions opened before the ban) gets a TCP reset. The filter chain runs at `filter - 10` and otherwise only accepts/rejects its own traffic, so ufw (currently inactive) is untouched — if ufw is ever enabled with default-deny, allow the responder port or banned clients get no message.
4. **Backend** (`backend/ftpban.py`, routes `/admin/ftpban/*`) bind-mounts `FTPBAN_DIR` **read-write** at `/ftpban` and reads/writes the same SQLite DB: manual bans, unbans, expiry changes and the settings row. The daemon applies them within ~2s. Settings `updated_at` must strictly increase (the daemon reloads on change). On startup the daemon writes any newly-added default keys into the stored settings JSON, since the backend returns that JSON as-is. nginx gives `/api/admin/ftpban/` its own `ftpban` limit_req zone.

5. **Watchdog / fail-open guardrail**: `ftpban/ftpban-watchdog.py` (→ `/usr/local/sbin/ciosuseradd-ftpban-watchdog`, oneshot service + `ciosuseradd-ftpban-watchdog.timer`, every 30s). Healthy = unit active + DB heartbeat < 20s + nftables sync OK + a loopback probe of the responder gets `421` (the table allows `iifname lo` to the responder port for this). Unhealthy → restart the daemon; still unhealthy on 2 consecutive runs → **fail open**: stop the daemon and `nft delete table inet ciosuseradd_ftpban`, so nothing is blocked. While failed open it retries every 10 min or when the portal sets status key `watchdog_retry` (`POST /admin/ftpban/watchdog/retry`). If the daemon unit is *disabled*, the watchdog only keeps the table removed. State in `FTPBAN_DIR/watchdog.json`, mirrored to status key `watchdog` (shown in the panel). Note non-banned clients never touch the responder — a responder outage only changes what *banned* IPs see; the guardrail exists so a hung/broken daemon can't leave stale, unexpirable bans in the firewall.

**Do not use ProFTPd's mod_ban for this.** `BanOnEvent` can't be limited to anonymous users (`ClientConnectRate` fires pre-login; `BanEngine` is read at session start), `ftpdctl ban` bans never expire, and on ProFTPd 1.3.8b a SIGHUP reload with mod_ban configured **segfaults the master** — fatal here, since new trusted/private users depend on reloads. Dry-run mode (`enforce=false`) records auto bans as `dry_run=1` "would ban" rows that are never enforced; manual bans are always enforced and ignore the whitelist. The whitelist lives in the settings row (`whitelist` = list the daemon reads, `whitelist_meta` = portal-only `{entry: {note, by, at}}`) and is edited only via `/admin/ftpban/whitelist` (Whitelist tab); `PUT /admin/ftpban/settings` keeps the stored whitelist rather than taking it from the form. Adding an entry lifts active auto bans it covers (`lifted_by='whitelisted'`) — the daemon only checks the whitelist before creating a ban.

**Threat whitelist (admin portal)** — separate from the FTP one: Postgres table `whitelisted_ips` (IP or CIDR), routes `/admin/whitelist/ips`, Whitelist tab in `panel-threats`. `ip_whitelisted()` in `admin_login` skips the banned-IP block, intrusion warning/escalation/lockout and all auto bans for those IPs (a wrong password is still a plain 401); manual IP bans of whitelisted IPs are refused, and whitelisting removes `banned_ips` rows in the range. `WRONG_PORTAL_NAME`/`WRONG_PORTAL_URL` (via `/public/site`) add a large "Trying to get to X? Please go to URL" box to the login page's warning overlay and failed-login messages.

### Download/upload activity pipeline

`logtailer/tailer.py` runs two threads (FTP, HTTP), each tailing a host log file/directory (mounted read-only) and writing rows to `db_logs`, tagged `source='ftp'|'http'`. On startup it also ingests any rotated/archived log files (`.gz`/`.tar.gz`/etc.) found in the same directory, tracked in `processed_archives` so each archive is only ingested once.

- FTP log line format: `[timestamp]|IP|USER|PATH|COMMAND|STATUS|BYTES` (pipe-delimited, 7 fields) — only `STATUS==226` rows are kept; `RETR` → downloads, `STOR`/`APPE` → uploads.
- HTTP log: tries the custom pipe format first (`parse_http_line`), falls back to standard nginx combined format (`parse_nginx_access_line`) for historical archives that predate the custom format.
- `username == 'anonftp'` (FTP) or `'-'` (HTTP) → `anon_downloads`/`anon_uploads`; anything else → `user_downloads`/`user_uploads`.

**R/W activity log (trusted + private users, `ftp_activity` in `db_logs`):** the backend publishes trusted/private usernames into `ftp_activity_users` (in `sync()`, `/admin/sync` and at startup — `publish_activity_users()`); the logtailer has no route to `db`, so this table is how it knows whom to track (refreshed every `CONFIG_POLL_INTERVAL`). The live FTP tail uses `parse_ftp_all()` = the existing download/upload row + `parse_activity_line()` (upload/download/delete/mkdir/rmdir/rename/chmod/login, success *and* failure, RNFR+RNTO paired per (user, ip) into one `rename` row with `path_from`). `tail_loop`/`ingest_archives` accept a parser returning a tuple *or* a list. One-time background backfill of the current FTP log (`tailer_config.activity_backfill_done`); the unique index `uq_fa_event` dedupes backfill/live overlap. Never pruned (the retention pruner only touches the download tables). `user_class` is the class at logging time. Routes `/admin/activity`, `/summary`, `/export`; panel `panel-activity`.

**Timestamps are real UTC everywhere.** ProFTPd (`[11/Oct/2026:17:17:02 -0400]`) and nginx `$time_iso8601` (`…-04:00`) log local time with an offset; `parse_ftp_timestamp()`/`parse_http_timestamp()`/`parse_nginx_access_timestamp()` all honour it. Until 2026-10-12 the first two dropped/overwrote the offset (local time stored as UTC); a one-time migration (`tailer_config.tz_migration_done`) shifted every affected row `(t AT TIME ZONE 'UTC') AT TIME ZONE 'America/New_York'`, with the original values kept in `db_logs.tz_fix_backup (tbl, id, old_logged_at)`. HTTP rows imported from the nginx *combined*-format archives (before 2026-05-30 22:51 UTC, plus their twins in the 05-30→06-11 overlap) were already correct and were not shifted. Repeated archive imports had duplicated whole days (HTTP 2026-05-31→06-10 at 3–11×, 06-23→06-26 at 2×; FTP anon 05-11 at 7×); on 2026-10-12 each such local day was deduped by its modal identical-row group size k (a group of s rows kept round(s/k)), preserving genuine same-second chunked requests. Removed rows are in `dedupe_backup_user_downloads` / `dedupe_backup_anon_downloads`. Identical rows on other days (a few %) are real download-manager chunk requests — don't "dedupe" them.

**Registered-vs-anonymous classification gotcha (`backend/logs.py`):** the shared public HTTP credential (`settings.public_http_username`, env `PUBLIC_HTTP_USERNAME`, the preserved first line of `.htpasswd`) is the *public* downloads login and is treated as anonymous everywhere in the UI, but it lands in `user_downloads` (not `anon_downloads`) because it authenticates like a named user. Any query that needs to split "registered users" from "anonymous" **must** go through `_registered_downloads_sql(source)` / `_anon_downloads_sql(source)` — never query `user_downloads`/`anon_downloads` directly for that split, or HTTP anonymous traffic gets miscounted as registered.

**Stats caching:** `stats_cache` table in `db_logs`, stale-while-revalidate via a shared `_swr(key, compute, ttl)` helper in `logs.py` — a value past its TTL is still returned immediately while a background thread recomputes and updates the cache; only a true cache-miss (`data is None`) blocks synchronously. All cached stats functions route through `_swr`; a new cached function should too rather than reinventing the cache dance. TTL scales with the window (`_ttl_for_days`: 5 min for 1d → 1h for >90d/all-time; `_TTL_SHORT` for the tiny upload tables). `_conn()` queues on `_pool_slots` (up to 20s) rather than failing when the 10-connection pool is empty. Background refreshes are capped at `_BG_SLOTS` (2) concurrent — don't remove that: uncapped, a page load touching dozens of stale keys exhausted the 10-connection pool, failing admin requests and making `_cache_set` silently discard minutes-long computes. `warmup_stats_cache()` runs **once at startup** only; don't reintroduce a periodic re-warm of every key — it kept `db_logs` at 100%+ CPU recomputing multi-million-row aggregates nobody was viewing. The download-stats `unique_*`/`total` figures come from `COUNT(*) OVER ()` / `SUM(...) OVER ()` on the top-N `GROUP BY` queries rather than a `COUNT(DISTINCT ...)` pass (which sorted every row and spilled TBs of temp files); this relies on `filename = basename(filepath)`. `db_logs` runs with tuned memory settings (`LOGS_PG_*` in `docker-compose.yml`, `shm_size` 1g). Cache values are JSON — `_json_safe()` converts `Decimal` (from Postgres `SUM(bigint)`) to `int`/`float` before serializing; don't reintroduce `json.dumps(..., default=str)` for cached numeric fields, since a `Decimal` silently round-tripping as a JSON *string* breaks frontend arithmetic (`a + b` becomes string concatenation) without erroring anywhere.

**Activity heatmap** (`get_activity_heatmap()`; `GET /admin/logs/heatmap` and unauthenticated `GET /public/overview/heatmap`, params `source`, `tz`, and `start`/`end` (ISO) or `days`, or neither for all history): a weekday × hour grid of all FTP or HTTP downloads (registered + anon, no split). The grid holds aggregate counts only, so the public route has nothing to mask. There is **one cached scan per source**, `_heat_series_all` (key `heat_all:{source}`, 6h TTL): every UTC epoch-hour bucket of all history, plus the hour it was computed. Each request slices that series in Python, tops it up with a live query for hours since the scan (`heat_tail:*`, a 60s `_cached_fresh`), and folds it into the viewer's timezone. Any range is cheap that way, recent hours are never stale, and DST is applied per hour. Don't move the range or timezone into SQL or the cache key. `slots` counts how often each weekday/hour occurred in the range, so the frontend can show per-hour averages. An unknown `tz` falls back to UTC. The UI is shared: `frontend/static/heatmap.js` (`HeatmapUI.createMap`/`createRangePicker`, presets + custom From/To; colour is green→red scaled to the 95th percentile) is used by the admin **Busiest Times** nav section (`panel-heat-ftp`/`panel-heat-http`) and by the bottom of `public.html` (both maps, own picker, refreshes every 5 min).

**Public dashboard** (`frontend/public.html`, `GET /public/overview/*` routes): reuses the exact same cached `logs.py` functions as the authenticated `/admin/logs/*` routes (so admin and public data are never computed differently), then masks IP/username **only in the route handler** — `_mask_ip()` blanks the last two IPv4 octets, `_mask_username()` keeps first+last char. Never add a field to a public route that isn't masked on the way out. Its time picker (`RANGES` in `public.html`) sends `days=` or, for sub-day windows, `minutes=`, accepted only from `MINUTE_WINDOWS` in `logs.py` (window → timeline bucket seconds; keep the frontend's `step` in sync). Minute windows go through `_cached_fresh` rather than `_swr`, with a seconds-long TTL: a stale value for a 1-minute window is simply wrong, so it recomputes in the request, single-flight per key. `top-stats` only accepts `days` from `_PUBLIC_TOP_STATS_DAYS`; those keys are pre-warmed because a cold 1y compute exceeds nginx's 30s proxy timeout. `/api/public/overview/` has its own nginx `public` limit_req zone (120 r/m): the page sends 7 requests per refresh, every 10s on the shortest ranges.

## Config

- `.env` is gitignored; `.env.example` is the template — keep both in sync when adding a new setting.
- `FTPD_PASSWD_DIR`, `FTP_BASE_PATH`, `HTPASSWD_DIR`/`HTTPASSWD_DIR` are **host** paths, bind-mounted into `backend` as `/ftpshared`, `/ftpbase`, `/httpshared` respectively.
- `FTP_LOG_DIR` / `HTTP_LOG_DIR` are **host** paths, bind-mounted **read-only** into `logtailer`.
- `FTPWHO_DIR` is a **host** path, bind-mounted **read-only** into `backend` at `/ftpwho`. It must match `Environment=FTPWHO_DIR=` in the systemd unit.
- **Keep the repo generic — no deployment-specific values in code.** Site name, public FTP host, and the public HTTP login come from `SITE_NAME`/`FTP_PUBLIC_HOST`/`PUBLIC_HTTP_USERNAME`, served unauthenticated by `GET /public/site` and loaded into the `SITE` object on both frontends (`siteReady` promise; initial data loads wait on it). The frontends strip `SITE.ftp_base_path` from displayed file paths. Never hardcode a hostname, path, IP, or username in code or docs; put real values only in `.env`. `PUBLIC_HTTP_USERNAME` is embedded directly in SQL in `logs.py`, which is why `config.py` validates it against `[A-Za-z0-9_.-]`.
- `ADMIN_USERNAME`/`ADMIN_PASSWORD` only seed `admin_config` on first boot; after that, admin credentials live in the DB and are managed via the Settings panel — changing the env vars later has no effect.
